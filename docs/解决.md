## 1. Judge 返回的不是合法 JSON —— 模型层

### 现象
评测跑完，一部分样本的指标分数直接报错；换个模型、换个样本，报错位置还不固定。

### 根因
我对 Judge 用了 `response_format={"type": "json_object"}` 强约束，但模型并不总是听话：有时候返回带 Markdown 代码围栏的 JSON，有时候返回 JSON 前后加了解释文字，有时候干脆拒答。**强约束把"模型偶发不守规矩"变成了"整条评测失败"。**

### 排查
把失败样本的原始返回打出来对比，发现分三类：带 ```` ```json ```` 围栏、前后有多余文字、以及完全不是 JSON。第三类才是真失败，前两类其实是"能解析但没解析"。

### 方案
两层：
1. **解析层容错**：`_parse_json_object` 先用 `json.loads`，失败再用正则从文本里抠出第一个 `{...}` 对象；
2. **请求层降级**：JSON 模式抛异常时，去掉 `response_format` 重新请求一次，成功则继续，仍失败才记为 error。

```python
# 简化的降级逻辑
try:
    resp = await call(..., response_format={"type": "json_object"})
except Exception as exc:
    logger.warning("Judge JSON mode failed, retrying without response_format: %s", exc)
    resp = await call(...)   # 不带 response_format 重试
```

### 效果
能解析的两种"脏 JSON"不再失败；模型不支持 JSON 模式时也能跑；真正的失败被清晰记为 error 而不是静默 0 分。

### 面试话术
> "这件事让我明白：**不要相信模型会遵守格式约束**。约束是提高成功率，不是保证。工程上必须假设它会失败，并且把失败分成'能救'和'不能救'两类。"

## 2. 改了配置，历史报告复算不一致 —— 架构层

### 现象
同一份历史评测报告，过一段时间再看，指标均值、通过率变了。追查发现没人改数据，是场景的阈值/权重/判据被别人调过。

### 根因
评测结果只存了分数，**没有存"当时是按什么标准打的分"**。配置文件是"活的"，历史结论是"死的"，两者一错位，报告就失去证据价值。

### 排查
对比两次读取同一任务的汇总结果，发现分数明细一致，但 pass/fail 判定不同 —— 定位到通过阈值变了。

### 方案
**场景快照冻结**：创建评测任务时，把当时的场景配置（指标列表、阈值、权重、`prompt_override`）整体序列化成 JSON 存进 `EvalTask.scenario_snapshot`。后续复算、报告对比、RSI 影子评测**只读快照，不读当前配置**。

```python
EvalTask(
    ...,
    scenario_snapshot=build_scenario_snapshot(scenario, payload.metric_overrides),
)
```

### 效果
历史报告永远可复现；回归对比有稳定基线；顺带解决了 RSI 的"候选配置怎么传"——候选只进快照，不碰线上实体。

### 面试话术
> "这本质上是**给评测做时间旅行防护**。配置是会漂移的，结论必须锚定在创建那一刻的标准上，否则三个月后的复盘就是在用新标准审判旧结果。"

## 3. 评分失败被当成 0 分 —— 指标语义

### 现象
某次批量评测通过率突然掉了 20 个点，大家以为模型退化了，结果一看是上游接口超时，一半样本根本没评出来。

### 根因
代码里把"没拿到分数"默认填了 0，导致**工程故障伪装成质量下降**。0 分和 error 混在一起，通过率、均值、失败数全部被污染。

### 排查
导出明细后发现：失败样本的 `metric_scores` 是 0，但 `execution_log` 里有超时记录。两者一对，才确认是故障不是退化。

### 方案
三处改：
1. 评分失败不写 0，写 `None` 并计入 `error_count`；
2. 汇总统计里 `error_count` 与 `pass_rate` 并列输出，不参与均值计算；
3. RSI 验收门禁加一条：**错误率上升不超过 0.02**。

### 效果
"测坏了"和"答得差"彻底分开；报告能一眼看出是质量问题还是稳定性问题。

### 面试话术
> "我总结了一条原则：**评不出来必须显式化，绝不能默认 0**。0 分是一个业务判断，error 是一个工程事实，两者的修复方向完全相反。"

## 4. 长任务阻塞接口，重启后任务永远转圈 —— 并发稳定性

### 现象
两个问题连着来：评测一跑，前端所有接口变慢甚至超时；服务重启后，数据库里一堆任务是 `running`，但进程早没了，前端永远等不到结果。

### 根因
- 评测是长耗时任务，直接在 FastAPI 事件循环里跑，会把整个服务卡住；
- 任务状态只在内存里推进，进程一重启，内存状态丢失，数据库状态却停在 `running`。

### 排查
观察接口响应时间随评测并发线性恶化，确认是事件循环被占；重启后对比数据库状态与进程列表，发现"running 但无对应进程"。

### 方案
1. **执行隔离**：用线程把长任务从事件循环摘出去，线程内部 `asyncio.run` 跑异步评测，接口立即返回，前端轮询进度；
2. **超时兜底**：RAG 生成任务设 15 分钟超时；
3. **僵尸回收**：`recover_stale_*` 在读取/启动时把超过时限的 `running` 任务标记为失败，保留已完成结果；
4. **并发限流**：盲测用信号量限制并发路数。

### 效果
接口响应不再受评测影响；重启后不会留下永远转圈的任务；超时任务保留已完成部分，不白跑。

### 面试话术
> "长任务要解决两个问题：**别阻塞**、**别留脏状态**。前者靠执行隔离，后者靠'状态机 + 超时回收'。我宁可把任务标记成失败，也不留一个永远 running 的僵尸。"

## 5. PDF 页眉页脚、OCR 乱码污染出题 —— 数据质量

### 现象
自动生成的 RAG 题目质量很差：问"这份文档的公司名称是什么"、"第 3 页写了什么"，答案全是页眉和页码。

### 根因
PDF 抽出来的文本是"版面文本"，不是"正文"。页眉页脚、页码、修订记录、表单回执反复出现，被当成正文分块，再被拿去出题，等于**用噪声训练评测**。

### 排查
抽样看分片内容，发现大量重复行；统计高频行，页眉出现次数和页数正相关，确认是重复行噪声。OCR 部分则是短英文串 + 极少中文，明显是识别失败。

### 方案
三套规则：
1. **重复行识别**：跨页高频重复的行判定为页眉页脚直接剔除（`_is_pdf_noise_line`）；
2. **乱码识别**：连续英文串且中文字符极少 → 判定 OCR 失败，整段过滤并说明原因；
3. **分片质量打分**：过滤类分片给 0 分并标注"页眉页脚/页码噪声"或"OCR 乱码"，低分分片减少或不出题。

### 效果
出题不再问元问题；样本带 `reference_context_ids` 时指向的是正文而非页眉。

### 面试话术
> "做 RAG 数据集最容易踩的坑是**以为抽出来就是正文**。我的做法是先给数据打分再出题——低质量分片宁可不出题，也不制造垃圾样本。垃圾样本比没有样本更糟，因为它会污染指标。"

## 6. 检索质量只能"感觉还行" —— 评测方法

### 现象
RAG 回答不好时，团队争论"是检索没找到，还是模型答歪了"，谁也说服不了谁，因为没有可量化的检索指标。

### 根因
生成侧有 Faithfulness 这类指标，但检索侧缺少"标准答案出自哪一段"的标注，导致检索质量无法独立计算，只能靠人看。

### 排查
发现生成的问答样本只有问题和答案，没有记录答案依据的分片 ID，所以无法判断"检索有没有命中正确证据"。

### 方案
1. 数据构建时给每条样本落 `reference_context_ids` —— 标准证据分片 ID；
2. 实现两个**确定性**检索指标：**HitRate@K**（前 K 个是否命中）与 **MRR**（命中排名的倒数）；
3. 与 LLM 侧的 Context Recall / Context Precision 配合，形成"检索 + 生成"双层指标。

### 效果
检索可以脱离 LLM 单独算，跑一百次结果一致，能直接做检索链路的回归测试；出问题时能判断是"没召回"还是"召回但排太后"。

### 面试话术
> "这一招叫**把'标准答案的出处'结构化**。一旦有了证据 ID，检索就从主观判断变成可计算的 HitRate 和 MRR，定位问题也从'吵'变成'看指标'。"

## 7. 盲测总把 A 放左边 —— 实验设计

### 现象
人工盲测的胜率明显偏向 A 侧，但把 A/B 顺序对调后再测，结论反过来。

### 根因
展示顺序固定为 A 左 B 右，评审存在**位置偏见**（先看到的更容易被偏好）。更麻烦的是，如果用 `random` 打乱，同一行第二天顺序会变，投票无法复核。

### 排查
做了一次对照：同一批样本正序测一遍、反序测一遍，胜率显著翻转，确认是位置效应而非质量差异。

### 方案
**确定性随机化**：用 `md5(task_id:row_id)` 的哈希值决定每一行的左右顺序。

```python
def _make_display_order(task_id: int, row_id: int) -> list[str]:
    digest = hashlib.md5(f"{task_id}:{row_id}".encode("utf-8")).hexdigest()
    # 依据 digest 决定 a/b 左右
```

### 效果
整体上 A/B 左右分布均衡，位置偏见被抵消；同一行任何时候打开顺序一致，投票可复核。结果同时输出 `ties`、`both_bad` 和未答样本，避免混进胜率。

### 面试话术
> "关键点是**随机要可复现**。`random` 能消偏见但没法复核，`md5` 两者都要。随机化是为了公平，确定性是为了审计。"

## 8. 不同口径的报告被拿去对比 —— 产品一致性

### 现象
用户拿 A 场景的报告和 B 场景的报告做对比，得出"新版更差"的结论，实际上是两套指标，根本不可比。

### 根因
对比接口只校验了任务存在，没校验**数据集、场景、指标集**是否一致。指标集不同时，缺失的指标被当成 0 参与对比，结论必然错。

### 排查
复现一次跨场景对比，看到缺失指标在结果里显示为 0，确认是"缺数据被当成了低分"。

### 方案
在对比接口加三道前置校验，任一不满足直接返回 422 并给出明确原因：
- 必须同一数据集；
- 必须同一场景；
- 指标集必须一致。

```python
if current.dataset_id != baseline.dataset_id:
    raise HTTPException(422, "只能对比同一数据集下的评测任务")
if current.scenario_id != baseline.scenario_id:
    raise HTTPException(422, "只能对比同一评测场景下的任务")
if current_metrics != baseline_metrics:
    raise HTTPException(422, "只能对比指标集一致的评测任务")
```

### 效果
从"算出一个错误结论"变成"直接告诉你不可比"。比错结论更危险的是**看起来合理的错结论**。

### 面试话术
> "我的原则是**宁可拒绝，也不给错答案**。对比这件事，不可比的时候返回 422 是正确行为，硬算出一个 delta 反而是产品事故。"

## 9. 自进化会"自己证明自己"、还会跑飞 —— 治理

### 现象
RSI 闭环做出来后，第一版有两个致命问题：
1. 用同一批样本做归因和验收，改完的标准当然"变好了"；
2. 偶尔一轮跑几十分钟、几十次模型调用，预算失控；重启后循环卡在 `running`。

### 根因
- **自证偏差**：归因和验收同源，等于用被改过的数据证明改动正确；
- **切分不稳定**：最初用随机切分，同一循环每轮留出集都变，跨轮结论不可比，还可能把上一轮验证过的样本重新跑回训练集，造成泄漏；
- **无预算约束**：迭代没有硬上限，异常情况下会一直跑。

### 排查
构造一个"故意放宽阈值"的提案，发现它在同源数据上必然通过 —— 直接证明自证偏差存在。

### 方案
**防自证三件套**：
1. **稳定切分**：`md5(f"{loop_id}:{dataset_row_id}")` 切 train/holdout，同一循环永远同一份切分（`rsi_policy.py:148`）；
2. **阈值冻结**：参考阈值在循环创建时从基线快照冻结（`rsi_policy.py:125`），验收不受候选配置影响；
3. **职责分离**：归因只读训练集，验收只读留出集，提案与验收是两段逻辑。

**防跑飞三件套**：
4. 预算硬上限：最多 3 轮 / 每轮 50 行 / 300 次调用 / 45 分钟 / 每轮 3 个提案；
5. 收敛终止：连续 2 轮无增益即停（`rsi_engine.py:108-117`）；
6. 重启回收：超过预算时长的 `running` 循环自动终止并记录原因（`rsi_engine.py:753-766`）。

### 效果
"放宽标准"的提案无法通过验收；跨轮结论可比；异常情况不会无限消耗；重启后不留僵尸循环。

### 面试话术
> "自进化最大的风险不是跑不起来，而是**它用自己改过的数据证明自己改得对**。所以我把归因和验收彻底隔离，阈值在开始时就冻结，版本表只增不改。宁可让机制笨一点，也不能让它自证。"

## 10. 接口凭据可能被 API 回显 —— 安全

### 现象
被测接口需要配置 Bearer Token / API Key。如果直接返回配置对象，前端和日志里就会出现明文凭据。

### 根因
ORM 模型和响应模型是同一份数据，`authorization` 字段原样序列化返回，一旦被日志、浏览器缓存或截图带出去就是泄露。

### 排查
抓一次 `GET /endpoint-targets` 的响应，确认 `authorization` 是明文；再看 `llm_config` 同样问题。

### 方案
1. 响应模型增加 `authorization_masked`，用 `mask_secret` 只保留首尾；
2. `hide_authorization` 在序列化前把明文置空；
3. 更新时若前端没传新值，保留数据库原值，避免"脱敏后回写把凭据清空"。

```python
def hide_authorization(self):
    self.authorization_masked = mask_secret(self.authorization or "")
    self.authorization = None
```

### 效果
接口不再回显明文；更新逻辑不会误清空凭据；日志和截图不再构成泄露面。

### 面试话术
> "安全这块我的原则是**凭据只进不出**。前端只能看到打码结果，更新时如果没传新值就沿用旧值——既要防泄露，也要防'脱敏导致误删'。"

## 附：一个"已知未完全解决"的问题（主动坦白，加分项）

### 权重配置存在，但未参与汇总
- **现状**：场景指标支持配置 `weight`，但汇总统计按指标等权输出 mean / pass_rate，权重未参与总分计算。
- **为什么当初这样做**：加权总分需要一套业务口径（不同指标量纲不同、方向不同），早期强行加权反而会产生"看起来精确但不可解释"的分数。
- **下一步**：在汇总层增加可选的加权公式，权重归一化后再计算，并在报告中显式标注"加权/非加权"。

**面试话术**：
> "这块我没做完，也不打算在简历里说成已完成。我更愿意说清楚为什么先不做——**加权的前提是量纲和方向统一**，否则加权分比不加权更容易误导。"

## 面试应答策略（怎么用这份文档）

### 1. 挑 3 个讲，不要讲 10 个
按岗位选：

| 岗位方向 | 推荐讲 | 理由 |
|---------|-------|------|
| AI 应用 / Agent 开发 | #3、#6、#9 | 体现评测思维 + 治理能力 |
| 后端 / 平台工程 | #2、#4、#10 | 体现架构、稳定性、安全 |
| 算法 / 评测 | #1、#5、#7 | 体现数据质量与实验设计 |
| 全栈 | #2、#4、#8 | 体现端到端与产品一致性 |

### 2. 每题控制在 90 秒
> 30 秒讲现象和根因 → 40 秒讲方案（说清楚"为什么这么选"） → 20 秒讲效果和一句总结。

### 3. 一定会被追问的三个点
| 追问 | 回答要点 |
|------|---------|
| "你怎么发现这个问题的？" | 说具体证据：日志、对比实验、复现路径，**不要只说'我发现'** |
| "有没有更好的方案？" | 给一个备选 + 说明取舍（例如随机切分 vs 哈希切分） |
| "这个方案有什么代价？" | 主动说缺点（哈希切分不随样本增删自适应、快照占存储、人工审批慢） |

### 4. 不要说的话
- ❌ "这个问题很轻松就解决了" → 显得没有深度
- ❌ "我们用了 XX 框架就好了" → 显得只会调库
- ❌ 编造百分比（"提升了 30%"） → 一问出处就崩
- ✅ 换成可验证的量：接口数、指标数、用例数、阈值、代码位置

> "这十个问题里，真正难的不是写代码，是**判断什么叫做对了**。评测系统的价值不在于给出一个分数，而在于这个分数能不能被复现、被解释、被审计。我做的所有设计——快照、error 分离、确定性指标、稳定切分、脱敏——都是在服务这一件事。"
