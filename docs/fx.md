# AI 评测平台功能完善建议（fx.md）

> 分析对象：AI Evaluation Platform（AI 评测平台）+ RSI 自进化模块
> 分析方式：基于当前代码库静态扫描（后端 79 个接口 / 10 个 API 模块，前端 16 页面 / 17 组件）
> 输出目标：给出**可执行、可排期、不过度设计**的完善清单
> 优先级定义：**P0 = 上线前必须做；P1 = 显著提升质量/效率；P2 = 增强与体验优化**

---

## 一、现状盘点（客观数据）

| 维度 | 现状 | 说明 |
|------|------|------|
| 后端接口 | 79 个 REST 端点，10 个 API 模块 | RSI 占 17 个，是最大模块 |
| 后端分层 | api / core / models / schemas | 分层清晰，职责基本到位 |
| 前端规模 | 16 个页面、17 个组件 | 以 Ant Design 中后台形态为主 |
| 评测内核 | 自研 LLM-as-a-Judge，22 个内置指标 | 不依赖第三方指标库 |
| 异步模型 | 线程 + `asyncio.run` + 前端轮询 | 单机可用，无消息队列 |
| 数据库 | SQLite，`eval_platform.db` 约 0.21 MB | 开发/SQLite；已装 `psycopg` 可切 PG |
| 迁移工具 | **无 Alembic**，靠 `create_all` + 运行时补列 | `core/database.py:63` |
| 认证授权 | **完全缺失**（无 JWT、无 RBAC、无登录） | 全库无 `get_current_user` |
| 测试 | 12 个测试文件（6 个 RSI 专项） | 覆盖核心策略与补丁逻辑 |
| 实时推送 | **未实现 WebSocket**；实际是 1~1.2 秒轮询 | 与 AGENTS.md 描述不一致 |
| 模型调用 | `timeout=180`、`max_retries=2`、低温 0.01 | 基础容错已有 |
| 成本计量 | **无 token / 成本统计** | 只有调用次数预算（RSI） |
| Prompt 管理 | 有模板与变量替换，**无版本号** | `core/prompt_manager.py` |

### 总体评价

| 能力 | 成熟度 | 判断 |
|------|--------|------|
| 评测内核与指标体系 | 高 | 可解释、可追溯，是真正的护城河 |
| RSI 自进化治理 | 高 | 留出集隔离、白名单、版本审计完整 |
| 前后端业务闭环 | 中高 | 功能完整，工程细节偏"能跑" |
| 生产化基础设施 | 低 | 认证、迁移、并发、成本四项是硬缺口 |
| 数据规模验证 | 低 | 当前为示例级数据，未做容量压测 |

**一句话结论**：**能力已经够"讲"，但还不够"上生产"**。最该补的不是功能，而是认证、迁移、并发与成本这四条工程底座。

### 前端建议的取舍说明

- **不建议**引入 Redux/MobX：当前页面级状态足够，引入只会增加复杂度。
- **不建议**自研组件库：Ant Design 已覆盖中后台场景，自研收益低。
- **建议优先做 F1/F2**：这两项直接影响后续所有迭代速度，属于"越晚做越贵"的技术债。

### 后端建议的取舍说明

- **B4 是"性价比最高"的一项**：改动集中在评测循环，不涉及架构，但直接决定评测吞吐。
- **B1 + B2 + B3 必须一起做**：认证要落库、迁移要建表、索引要随迁移走，分开做会返工。
- **B6 可以延后**：单机线程模型在团队规模小的时候够用，等出现"多实例/任务重试"需求再上队列，避免过早复杂化。

## 四、AI 服务完善建议

| # | 问题 | 当前现状（证据） | 建议方案 | 收益 | 优先级 | 工作量 |
|---|------|-----------------|---------|------|--------|--------|
| A1 | 无成本计量 | 无 token / 费用统计；仅 RSI 有"调用次数"预算 | 每次调用记录 `prompt_tokens / completion_tokens / 估算成本`，按任务聚合 | 成本可见、可预算、可优化 | **P0** | 1.5 天 |
| A2 | 无结果缓存 | 相同样本+指标重复评测会重复调模型 | 以 `hash(row)+metric+prompt_version+model` 为键缓存评分结果，可开关 | 回归评测成本显著下降 | **P0** | 1.5 天 |
| A3 | Prompt 无版本 | `prompt_manager.py` 只有模板与变量替换，无版本号 | 给 Prompt 加 `version`，并写入 `scenario_snapshot` 与结果记录 | 结论可追溯到"哪版判据" | **P0** | 1 天 |
| A4 | 单模型无降级 | 仅 JSON 模式失败降级重试（`evaluation_engine.py:90-103`） | 配置主/备模型，主模型连续失败切备用；记录切换原因 | 评测不因单模型故障中断 | P1 | 1.5 天 |
| A5 | Judge 可信度未校准 | 低温 0.01 + 结构校验，但无人机一致率 | 建"黄金集"（人工标注），定期跑一致率与漂移告警 | 证明评分可信，可对外交付 | P1 | 3 天 |
| A6 | 关键指标单次采样 | 每指标一次调用 | 关键指标重复采样 2~3 次取均值/中位数，并记录方差 | 降低评分随机波动 | P1 | 1 天 |
| A7 | 无 Provider 限流 | 未按 RPM/TPM 控制 | 按 provider 维度令牌桶限流 + 指数退避重试 | 避免 429 雪崩 | P1 | 1 天 |
| A8 | 检索指标覆盖有限 | 仅 HitRate@K / MRR + LLM 侧指标 | 增加 embedding 相似度、Rerank 前后对比、上下文去冗余率 | 检索问题定位更细 | P2 | 2.5 天 |
| A9 | 无多模态能力 | 仅扫描 PDF 的 OCR（文档解析，非多模态推理） | 如需扩展：样本增加 image 字段 + 视觉模型指标 | 覆盖图文场景 | P2 | 4 天 |
| A10 | 数据集分布单一 | `reference_context_ids` 同源切分 | 增加对抗集/跨场景集，用于 RSI 泛化验证 | 防过拟合，提升结论可信度 | P2 | 3 天 |
| A11 | 指标扩展性 | 22 个内置指标，新增需改引擎 | 抽象指标插件注册表（`metric_type -> 执行器`） | 第三方/业务自定义指标低成本接入 | P2 | 3 天 |
| A12 | 无评测结果置信区间 | 只输出点估计 | 汇总处输出 bootstrap 置信区间 | 报告更严谨，支撑上线决策 | P2 | 2 天 |

### AI 服务建议的取舍说明

- **A1 + A2 + A3 是"先能算账，再谈优化"**：没有成本、缓存、版本这三项，后面所有优化都无法量化收益。
- **A5 黄金集是可信度的关键**：现在能证明"机制正确"，但证明不了"评分准确"；这是从项目走向产品的分水岭。
- **A9 多模态不建议现在做**：项目当前定位是文本评测，贸然加视觉会让指标体系和样本模型复杂度翻倍，且没有真实业务驱动。
- **A11 插件化要晚做**：只有确认"指标会持续大量新增"时才值得抽象，否则是过度设计。

## 七、明确不建议做的事（防止过度设计）

| 不做的项 | 原因 |
|---------|------|
| 引入 Redux / MobX / Zustand | 页面级状态够用，引入会增加心智负担 |
| 自研 UI 组件库 | Ant Design 已覆盖，自研无收益 |
| 现在就上微服务 | 单模块、单团队，拆分只会增加部署与联调成本 |
| 现在就做多模态 | 无真实业务驱动，指标体系会被迫复杂化 |
| 现在就做指标插件市场 | 指标增长未验证，抽象过早 |
| 为 SQLite 做复杂优化 | 正确做法是换 PG，而不是优化 SQLite |
| 追求 100% 测试覆盖率 | 应优先覆盖关键路径与边界，而非数字指标 |
