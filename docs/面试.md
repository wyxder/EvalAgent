# 面试讲解手册：Agent 与 RSI 自进化评测中台

> 适用场景：2026 长沙 CSDN Agent 创新赛决赛答辩 / AI 全栈工程师岗位面试
> 使用方式：先背 §1 开场与 §2 主线（这两块决定第一印象），再按面试官兴趣挑 §3、§4 深挖。
> 核心原则：**先讲人话，再讲术语；先讲痛点，再讲方案；每个亮点都落到一个可验证的数字。**

## 1. 开场自我介绍（三段，按时间挑一段）

### 1.1 30 秒版（自我介绍开场，不展开项目）

> 面试官您好，我是 XXX，主要做 AI 全栈开发。我的工作重心是把大模型能力真正落到业务里，所以除了前端和后端，我特别关注一件事——**怎么证明 AI 应用"变好了"**。我独立做过一个 AI 评测中台，覆盖 RAG、Agent、多轮对话三类场景，从数据集构建到自动评分、人工复核、A/B 盲测，最后还做了一层 RSI 自进化闭环。今天想重点跟您聊聊这个项目。

**为什么这么说**：一句话把"全栈"和"AI 评测"两个标签同时立住，并且埋了钩子（RSI），引导面试官往你擅长的方向问。

### 1.2 1 分钟版（HR 面 / 初面）

> 我是 XXX，做 AI 应用开发，偏全栈。我做过一个 AI 评测平台，解决的问题是：团队要换模型、换 Prompt、换检索策略的时候，往往靠感觉决定，出了问题也说不清是检索不行、还是模型不行、还是 Prompt 写得不好。
>
> 我的做法是把评测做成一条工程流水线：数据集 → 场景 → 指标 → Judge 模型打分 → 报告 → 人工复核 → A/B 盲测。相当于给 AI 应用建了一套"体检中心"，而且每一项检查都带医生的诊断理由，不是只给一个分数。
>
> 这个项目里我最有成就感的是最后加的 RSI 自进化模块：它能让评测系统自己从失败样本里总结问题、提出改进方案，再拿留出数据验证有没有真的变好。但最终采不采纳由人决定，防止"自己给自己打分"。
>
> 技术上是 React + TypeScript 前端、FastAPI + SQLAlchemy 后端，评测内核是我自己写的 LLM-as-a-Judge。

### 1.3 2 分钟版（技术面，讲完直接进项目）

> 我是 XXX，AI 全栈工程师，平时前后端都写，重点在 LLM 应用的工程化落地。
>
> 我想讲的项目叫「Agent 与 RSI 自进化评测中台」。起因很具体：我们评估一个 RAG 或 Agent 应用，通常只看最终回答"像不像样"，但这个回答背后有四段链路——数据、检索、模型、Prompt。只看结果，等于车子抛锚了只知道"车不走了"，不知道是油没了还是轮胎爆了。
>
> 所以我把它拆成三层：
> 第一层是**可解释的评测**，自己写了一个 LLM-as-a-Judge 内核，22 个内置指标，每个指标都会输出分数和不超过 800 字的评分理由，保证"为什么扣分"能追溯。
> 第二层是**场景化**，RAG、Agent、多轮对话各有一套模板，指标、阈值、权重都能按场景覆盖，因为这三类应用的评判标准本来就不一样。
> 第三层是**证据互补**，自动评分之外，还有人工复核和 A/B 盲测，用 MD5 哈希把每一行 A/B 顺序随机化，避免"总把 A 放左边"带来的位置偏见。
>
> 最后一层是我最近做的 RSI 自进化：系统从失败样本里做归因，生成改进提案，比如改写指标判据、调阈值，然后在固定的留出集上跑影子评测验证，通过门禁才允许写回。这块我花了最多心思在"防自证"上——归因只看训练集，验收只看留出集，阈值在循环创建时就冻结，版本表只增不改，随时能回滚。
>
> 整个项目是 React + FastAPI 全栈自研，评测内核没有依赖第三方指标库，因为我需要完全掌控评判口径和可解释性。

**关键动作**：讲完停住，看面试官眼神。如果他追问"防自证"或"Judge 怎么保证稳定"，就进入你的主场。

## 2. 项目讲解主线（三档，按场合用）

### 2.1 电梯版（30 秒，适合"简单介绍下这个项目"）

> 一句话：**给 AI 应用做体检，还能自动开药方、并且验证药效。**
> 体检 = 数据集 + 指标 + Judge 打分 + 报告；
> 开药方 = RSI 从失败样本归因出问题，生成配置改进提案；
> 验证药效 = 在固定留出集上跑影子评测，过门禁才写回，可回滚。

### 2.2 标准版（2–3 分钟，五段式，强烈建议背熟）

| 段落 | 时长 | 讲什么 | 关键句 |
|------|------|--------|--------|
| ① 痛点 | 20s | 换模型靠拍脑袋、出问题定位不到环节、结论无法沉淀 | "只看总分，等于只知道车不走了" |
| ② 定位 | 20s | 端到端评测工作台，不是单点工具 | "从数据集到结论的一条流水线" |
| ③ 架构 | 40s | 前端 React、后端 FastAPI、内核自研 Judge、场景快照冻结 | "评测内核我自己写的，因为口径必须可控" |
| ④ 亮点 | 60s | 挑 3 个讲：可解释 Judge / 异构样本统一建模 / RSI 自进化 | "每个分数都有理由，每个改进都可验证" |
| ⑤ 结果 | 20s | 22 指标、3 场景、17 个 RSI 接口、42 个 RSI 用例 | "不是 demo，有测试兜底" |

**标准版逐字稿**：

> 这个项目要解决的是一个很实际的问题：团队要决定"要不要换模型、要不要换检索方案"，但手上只有零散的脚本和主观感觉，出了问题也无法定位是数据、检索、模型还是 Prompt 的锅。
>
> 所以我把它做成一条完整流水线：左边是数据集构建，中间是场景和指标配置，右边是 Judge 自动评分、报告、人工复核和 A/B 盲测。核心设计是"场景快照"——每次评测把当时的指标配置冻结一份存进任务里，这样三个月后回看，结论还是可复现的。
>
> 架构上前端是 React + TypeScript + Ant Design，后端是 FastAPI + SQLAlchemy。评测内核是我自己写的 LLM-as-a-Judge，没有直接用第三方指标库，因为业务判据需要能被覆盖、评分理由需要能被追溯，第三方库这两点都不好控。
>
> 亮点我挑三个说：第一，22 个内置指标，每个都持久化分数和评分理由；第二，RAG、Agent、多轮对话三类场景各有模板，指标和阈值可以按场景覆盖；第三，最近做的 RSI 自进化，能把失败样本变成可验证的配置改进提案，但采纳权在人，且全程可回滚。
>
> 结果上，RSI 这块落地了 4 张表、17 个接口、7 个前端组件、42 个测试用例，验收门禁是目标增益不低于 0.03、受保护指标降幅不超过 0.02。

## 3. 七大模块讲解语录（对应简历 7 条）

> 每个模块统一三段式：**一句话讲法（给面试官）→ 展开讲法（技术细节）→ 引导话术（把话题拉到你擅长的地方）**

### 3.1 指标体系（简历第 1 条）

**一句话讲法**
> 指标不是一堆名字，而是一套"可配置的评分合同"——同一个指标在不同场景可以有不同的阈值、权重和判据。

**展开讲法**
> 我预置了 RAG、Agent、多轮对话三套场景模板。每个场景下的指标有三层可配：第一层是 `pass_threshold`，这条样本算不算过；第二层是 `weight`，这个指标在场景里占多重；第三层是 `prompt_override`，允许业务方用自己的话重写评判规则。
>
> 汇总的时候按指标维度输出 mean、min、max、pass_rate、error_count 五个统计量。为什么要有 error_count？因为"评分低"和"根本没评出来"是两回事，前者是质量问题，后者是工程问题，混在一起会误判。
>
> 这里有个我特意做的设计：**内置指标只读，业务判据通过 override 覆盖**。这样既保证系统级评分格式稳定，又让业务能定制，不会因为某个业务改了判据把整个 Judge 契约搞崩。

**引导话术**
> "这套设计的核心是**可配置但不失控**，我后面在 RSI 里也是同一个思路——只允许改白名单里的字段。"

### 3.2 RAG 评测（简历第 2 条）

**一句话讲法**
> RAG 评测要同时看"找得对不对"和"答得实不实"，只评一半等于没评。

**展开讲法**
> 数据集这块，我做的是文档到问答样本的自动构建。PDF 解析不是简单抽文本，要处理页眉页脚、页码、修订记录、表单回执，还有扫描件的 OCR 乱码，这些噪声进了分块会直接污染题目质量。
>
> 分块支持结构化和定长两种模式，默认 900 字、重叠 120 字。900 是我按中文语义密度和模型上下文权衡的，重叠 120 是为了不让跨段落的答案被切断。
>
> 出题之后还有二次校验和去重，特别要剔除"文档里提到了什么"这类元问题——这种题模型不需要理解也能答对，会虚高分数。
>
> 指标分两侧：检索侧用 Context Recall、Context Precision、Contextual Relevancy，再加两个确定性指标 HitRate@K 和 MRR；生成侧用 Faithfulness、Factual Correctness、Answer Relevancy、Answer Completeness。
>
> 关键点是我在样本里存了 `reference_context_ids`，也就是标准证据分片 ID。有了它，检索指标可以脱离 LLM 直接算，等于给检索链路做了单元测试。

**引导话术**
> "这里最能体现工程思维的是 `reference_context_ids`——把'标准答案出自哪一段'变成结构化字段，检索就从'感觉召回得还行'变成可计算的 HitRate 和 MRR。"

**可能追问**：HitRate@K 和 MRR 怎么算？
> HitRate@K：看前 K 个召回片段里有没有命中标准证据，有就是 1，没有就是 0，最后取平均。MRR 是命中片段的排名倒数，命中的越靠前分数越高。这两个指标不需要 LLM，所以完全可复现，适合做检索侧的回归测试。

### 3.3 Agent 评测（简历第 3 条）

**一句话讲法**
> Agent 评测不能只看最后那句话，要看它"用没用对工具、传没传对参数、有没有绕远路"。

**展开讲法**
> Agent 我分两类指标。一类是 LLM 侧，Task Completion、Goal Accuracy，判断任务有没有闭环，这类需要 Judge。
>
> 另一类是三个确定性指标，完全不依赖 LLM：
> - **Tool Correctness**：工具名和参数是否完全匹配；
> - **Argument Correctness**：工具名对上了，参数匹配度多少，支持嵌套结构；
> - **Step Efficiency**：实际步数和期望步数的偏差惩罚，绕远路要扣分。
>
> 为什么一定要有确定性指标？因为 LLM 评判有随机性，同样的输入两次可能给不同分。工具调用这种"有客观标准答案"的东西，就不该交给 LLM 猜。这三个指标是纯计算的，跑一百次结果一样，可以直接放进 CI 做回归。

**引导话术**
> "我对指标的分类原则是：**能确定性计算的，绝不交给 LLM**。LLM 只负责那些真正需要语义判断的部分，这样既省钱又稳定。"

### 3.4 原生 Judge 引擎（简历第 4 条）

**一句话讲法**
> 评分这件事，我不接受"黑盒给个 0.8 分"，我要它说清楚为什么是 0.8。

**展开讲法**
> 内核是自己写的，统一了一个指标执行层，按指标类型分四条执行路径：LLM 语义指标、确定性检索指标、确定性 Agent 指标、用户自定义 Prompt 指标。
>
> 自定义 Prompt 指标支持三种输出模式：numeric 打分、discrete 离散枚举、aspect_critic 分维度点评。
>
> 工程上有两个关键约束：
> 第一，**Judge 只能依据样本里给的字段打分，禁止引入外部知识**，否则它可能用自己训练时的记忆去"帮"被测系统答对，评测就失真了。
> 第二，**强制返回严格 JSON `{score, reason}`**。但模型不一定听话，所以我做了降级重试——如果 JSON 模式失败，就去掉 `response_format` 再请求一次，仍然失败才记为 error，而不是直接给 0 分。这点很重要：**评不出来必须和评为 0 分区分开**。
>
> 最终沉淀了 22 个内置指标，每条样本每个指标都持久化 score 和不超过 800 字的理由。800 字是截断上限，避免单条理由把数据库和前端撑爆。

**引导话术**
> "这块我最想强调的是**失败要显式化**。评分失败记 error，不记 0 分，因为 0 分是'答得差'，error 是'没测成'，两者混在一起会让通过率失真。"

**可能追问**：Judge 的随机性怎么控？
> 三层：一是温度压到很低；二是结构化输出 + 严格校验；三是把能确定性算的指标移出 LLM。另外在 RSI 的验收里，我加了 judge drift 门禁，容忍度 0.15，超过就说明评分本身不稳，这次演化结论不可信。

### 3.5 A/B 盲测（简历第 5 条）

**一句话讲法**
> 自动指标回答"合不合格"，盲测回答"用户更喜欢哪个"。

**展开讲法**
> 支持三类对比：LLM 对 LLM、Endpoint 对 Endpoint、LLM 对 Endpoint。
>
> 核心设计是**用 MD5 哈希对每一行随机化 A/B 展示顺序**。为什么不直接用 random？因为 random 不可复现——评审第二天回看，顺序变了，投票就没法复核。用 MD5 做确定性哈希，同一个样本每次打开顺序一致，但整体上 A 和 B 左右分布是均衡的，位置偏见被消掉了。
>
> 结果统计输出 model_a_wins、model_b_wins、ties、both_bad，还有未答样本。未答要单独统计，因为它既不是赢也不是输，混进胜率会误导。

**引导话术**
> "这里体现的是**可复现的随机**：随机化是为了消偏见，确定性是为了能复核，两者不矛盾。"

**如果被问"盲测样本量够吗、做显著性检验了吗"**（诚实回答）
> "目前是描述性统计，输出胜率和 ties，还没做显著性检验，这是明确的短板。如果要支撑上线决策，下一步应该加置信区间，比如用 bootstrap 估计胜率的波动范围，样本量至少要够到能区分 5% 的差异。我在 RSI 的验收里已经用了类似的思路——目标增益门槛 0.03，就是为了过滤噪声级别的提升。"

### 3.6 RSI 自进化（简历第 6 条）★ 主场

**一句话讲法（通俗版，先讲这个）**
> 传统评测是"体检报告"，看完还得人自己想办法。RSI 是"体检 + 医生开药 + 吃药后复查"，但**处方要主治医生签字**，而且每一步都有病历。

**一句话讲法（技术版）**
> 一个「失败归因 → 优化提案 → 影子回归 → 验收写回」的闭环，让评测系统依据自己的失败样本，提出并验证对评测配置的改进。

**展开讲法（按闭环四步 + 两道保险）**

> **第一步，失败归因。** 从评测结果里把失败样本捞出来，分两层归因：一层是规则聚类，按指标、分数区间、错误类型这些确定性特征先分堆；另一层是 LLM 聚类，让它总结"这批失败是不是同一个病因"，比如判据有歧义、标注有问题、被测系统本身有缺陷。LLM 挂了会自动降级到规则聚类，不会因为一次接口失败整个流程就断。
>
> **第二步，优化提案。** 根据归因结果生成配置改动提案，比如改写某个指标的判据、调整通过阈值、补一批困难样本。每个提案都是一条结构化的 patch，带 before_value 和 after_value，不是一段自然语言建议。
>
> **第三步，影子回归。** 把候选配置塞进一个"影子评测任务"的 `scenario_snapshot` 里，复用原有的 `run_evaluation` 跑一遍。注意是复用同一个引擎，不是另写一套评分逻辑——否则候选和基线就不可比了。影子任务不影响原场景，也不污染历史任务。
>
> **第四步，验收写回。** 拿留出集上的结果过门禁：目标指标增益不低于 0.03、受保护指标降幅不超过 0.02、新增失败 0 条、错误率上升不超过 0.02。全过了才允许写回，并且默认需要人工审批。
>
> **两道保险最关键：**
> 第一道是**防自证**。归因只能看训练集，验收只能看留出集，两边用 MD5 稳定哈希切分，比例默认 0.3。为什么用哈希不用随机？因为同一个循环反复跑，切分必须稳定，不然每次重跑留出集都变，历史结论就没法比了。而且参考阈值在循环创建那一刻就从基线快照里冻结了，防止"边改标准边验收"。
> 第二道是**防乱改**。patch 走字段级白名单，只有 4 类对象、8 个字段可改，文本长度不超过 4000，阈值单轮变化不超过 0.15。还做了凭据检测，出现 `sk-` 或 `Bearer` 直接拒；模板里出现 authorization、api_key、extra_headers 也直接拒。写回前要二次校验 before_value 是否和冻结快照、以及实时实体都对得上，防止这中间有人手动改过配置导致覆盖。

**数字落点**
> 4 张表：`rsi_loops`、`rsi_iterations`、`rsi_proposals`、`rsi_config_versions`。
> 版本表是 append-only 的，只允许打回滚标记，不允许改历史行——审计要求。
> 17 个 REST 接口、7 个前端组件、2 条前端路由。
> 6 个测试模块、42 个测试用例，覆盖策略、补丁、引擎、回滚、归因和 API。
> 预算硬约束：最多 3 轮、每轮最多 50 行、300 次 LLM 调用、45 分钟、每轮最多 3 个提案；连续 2 轮没增益就收敛；重启后会把超预算的"运行中"循环自动回收成失败，不留脏状态。

**引导话术**
> "这个模块我投入最多的地方其实不是算法，是**治理**。自进化最大的风险不是跑不起来，而是它用自己改过的数据证明自己改得对。所以我花了很多精力在隔离和审计上。"

### 3.7 评测报告（简历第 7 条）

**一句话讲法**
> 报告不是一张分数表，是"能定位到第几行、能说清为什么、能跟上一版对比"的证据链。

**展开讲法**
> 报告详情逐条展示每个指标的得分、Judge 理由、是否通过，接口评测还会带 trace——状态码、延迟、原始响应，失败可以直接定位到是哪一行、哪个字段没抽出来。
>
> 人工复核有独立的字段：状态、分数、备注，机器评分和人工判断是分开存的，不覆盖。这样后面可以算"机器和人的一致率"，这是判断 Judge 靠不靠谱最直接的证据。
>
> 报告对比支持当前 vs 基线，输出指标均值 delta、通过率 delta、失败数和错误数的变化，还能下钻到逐行差异。

**引导话术**
> "我做报告的原则是**结论必须能下钻到证据**。面试官问'这个 0.72 分怎么来的'，我能一直点到那一行样本和那段评分理由。"

## 4. 高频问题与参考回答

> 标注 ⭐ 的是大概率会问的核心题，建议逐字背。回答统一用"结论先行 + 一句解释 + 一个例子/数字"。

### A. 项目与架构

**A1 ⭐ 这个项目是你一个人做的吗？你负责哪部分？**
> 是独立完成的。从数据库设计、评测内核、API、前端页面到测试都是我自己写的。如果面试官问到具体代码，我可以直接讲某个模块的实现，比如 RSI 的 patch 校验或者 Judge 的降级重试。

**A2 ⭐ 为什么选 FastAPI 而不是 Django / Spring Boot？**
> 三个原因。第一，评测是 IO 密集型，大量时间在等 LLM 返回，FastAPI 原生 async 能把并发做起来。第二，Pydantic 做请求校验和响应模型很顺手，评测这种字段多、结构复杂的场景收益明显。第三，自动生成 OpenAPI 文档，前后端联调成本低。
> 如果业务是重后台管理、需要大量现成 CRUD，我会选 Django；如果是大团队强类型约束，Java 也合理。这个项目的特点是"异步 + 结构化数据 + 快速迭代"，FastAPI 最匹配。

**A3 ⭐ 为什么用 SQLite？数据量大了怎么办？**
> SQLite 是为了零配置、可一键体验，适合单机和小团队。我通过 `DATABASE_URL` 做了抽象，换 PostgreSQL 不需要改代码。
> 真上生产我会换 PG，原因有三个：一是评测结果行数增长快，PG 的索引和分区更稳；二是 SQLite 是单写锁，后台任务并发写会排队；三是 PG 支持 JSONB，我的快照和指标结果都是 JSON，用 JSONB 可以下推查询。
> 另外现在没上 Alembic，是靠 `create_all` 加一个运行时补列的兜底函数。上生产前这个必须换成正式迁移。

**A4 ⭐ 后台任务为什么用线程 + asyncio，不用 Celery？**
> 这是有意的取舍。Celery 要额外部署 broker（Redis/RabbitMQ），对一个单机就能跑起来的评测平台来说，部署成本高于收益。我的做法是用线程把长任务从 FastAPI 事件循环里摘出去，线程内用 `asyncio.run` 跑异步评测，这样既不阻塞接口响应，又不需要外部依赖。
> 代价是：任务不能跨进程分发、重启会丢内存里的任务状态。所以我在启动时加了"陈旧任务回收"，把状态还是 running 但实际已经死掉的任务标记为失败，保留已完成的结果，不留脏状态。
> 如果要做多机、要任务重试和优先级队列，那 Celery 或 RQ 就是必须的，我会毫不犹豫换掉。

**A5 ⭐ 场景快照是什么？为什么需要它？**
> 每次创建评测任务时，把当时的场景配置——包括指标列表、阈值、权重、prompt_override——序列化成一份 JSON 存进任务里。
> 为什么需要？因为配置是会变的。如果三个月后有人改了阈值，回头再看历史报告，用新配置复算会得到不同结论，那这个报告就没有证据价值了。快照的意义是**让历史结论永远可复现**，本质是评测领域的"时间旅行防护"。
> RSI 也是靠这个机制做影子回归的——候选配置只通过快照传进去，不碰线上实体。

**A6 如果评测任务重复触发怎么办？**
> 接口层对同一循环做了状态守卫，运行中的不允许再次启动，重复请求返回 409。任务内部按行写入结果，重跑会覆盖同一行的结果而不是追加，保证幂等。

**A7 前端为什么用 Ant Design？**
> 这个项目大量是表格、表单、抽屉、时间线，Ant Design 在这些中后台组件上成熟度高，能省掉大量基础组件开发。TypeScript 严格模式加上统一的 types 目录，接口字段改了编译期就能发现。

**A8 你觉得这个项目的技术难点在哪？**
> 三个。第一是**评测的可信度**，Judge 是概率模型，怎么让它的结论稳定、可解释、可复现。第二是**异构样本的统一建模**，RAG 要上下文、Agent 要工具调用链、多轮对话要轮次结构，得用一套 schema 装下。第三是**自进化的治理**，怎么防止它自证和乱改。
> 这三个里我投入最多的是第三个，因为它不只是技术问题，还是流程和审计问题。

### B. 指标与 Judge

**B1 ⭐ 22 个指标是怎么来的？**
> 按场景分类设计的。RAG 侧分检索和生成两组，检索有 Context Recall、Context Precision、Contextual Relevancy、HitRate@K、MRR，生成有 Faithfulness、Factual Correctness、Answer Relevancy、Answer Completeness。Agent 侧有 Task Completion、Goal Accuracy、Tool Correctness、Argument Correctness、Step Efficiency。多轮对话侧有 Topic Adherence、Turn Relevancy、Conversation Completeness、Knowledge Retention、Role Adherence。再加上通用的和自定义的，一共 22 个。
> 分类原则是：**能用确定性规则算的，就不放进 LLM 指标**。

**B2 ⭐ LLM-as-a-Judge 靠谱吗？怎么保证它打的分可信？**
> 我的看法是：Judge 不是"可信"，是"可校准"。它不是替代人，是替代人做重复劳动，然后用人做抽样校准。
> 具体四招：第一，约束输入，只给它样本里该看的字段，禁止引入外部知识；第二，结构化输出，强制 `{score, reason}`，失败降级重试，评不出来记 error 不记 0 分；第三，把工具调用、检索命中这类有客观答案的指标移出 LLM；第四，保留人工复核字段，可以统计人机一致率。
> 如果要进一步，我会加"黄金集"——人工标注一批标准样本，定期跑 Judge 看一致性有没有漂移。

**B3 ⭐ temperature 怎么设的？为什么要低？**
> 评测要的是可复现，不是创意。温度高会导致同一份答案两次评分不一样，报告就没有证据价值了。所以评分走低温，提案生成可以稍高一点，但我也限制在 0.2，避免提案太发散。

**B4 Judge 有位置偏见、长度偏见吗？怎么处理？**
> 有，这是 LLM 的已知问题。我做了两件事：一是指标级别尽量拆细，不让一个笼统的"整体质量"承担所有判断；二是 A/B 盲测用哈希随机化顺序，直接把位置偏见消掉。长度偏见目前主要靠 prompt 里明确要求"不因答案长短加减分"，但没有做严格的对照实验，这是可以继续做的。

**B5 通过率是怎么算的？阈值 0.7 合理吗？**
> 单指标层面，score 大于等于该指标的 pass_threshold 就算这一项通过，默认 0.7；样本层面，所有指标都通过才算这条样本通过。通过率就是通过样本数除以有效样本数。
> 0.7 是经验默认值，不是拍脑袋——它对应"基本合格但还有改进空间"。但我把它做成可配的，因为不同业务容忍度不一样：医疗问答可能要求 0.9，闲聊 0.6 就够。这也是我设计场景化指标的原因。

**B6 ⭐ error 和 0 分为什么要分开？**
> 因为含义完全不同。0 分是"模型答错了"，error 是"这次没测成"——可能接口超时、可能 Judge 返回了非法 JSON。如果 error 记成 0 分，通过率会被凭空拉低，你会误判成质量下降，实际上只是工程故障。
> 所以汇总里专门有 error_count，RSI 的验收门禁里也有一条是"错误率上升不超过 0.02"。

**B7 自定义 Prompt 指标支持哪几种模式？**
> 三种：numeric 让模型打连续分，discrete 让它从枚举里选，aspect_critic 让它按维度分别点评再汇总。区别在于业务问题适合哪种表达——满意度适合 numeric，合规检查适合 discrete，内容质量适合分维度点评。

**B8 800 字截断会不会丢信息？**
> 会丢，但这是有意的。理由文本主要用于人看和归因，800 字足够说清扣分点。无上限的话，长理由会撑大存储、拖慢前端渲染，而且归因时还要再截断一次。与其两处都截，不如在写入时就统一截断。

### C. RAG

**C1 ⭐ PDF 解析最难的地方是什么？**
> 噪声，不是解析本身。真实 PDF 里有页眉页脚、页码、修订记录、表单回执、水印，这些东西混进正文，分块之后就会污染题目。比如页眉反复出现公司名，模型会以为这是重点内容。
> 所以我在解析后做了一层噪声治理，包括 OCR 乱码识别过滤。扫描件走 PyMuPDF 渲染加 Tesseract OCR，中英文一起识别。

**C2 ⭐ 分块为什么是 900 字、重叠 120？**
> 900 是权衡结果：太短语义不完整，问题会缺上下文；太长会引入无关内容，检索精度下降。中文 900 字大概是一个完整小节的量级。重叠 120 是为了防止答案正好跨在两个块的边界上，被切断后两边都不完整。
> 这两个值我做成了可配，结构化分块按标题层级切，定长分块按字数切，让用户按文档类型选。

**C3 ⭐ 怎么保证自动生成的题目质量？**
> 四道关。第一，先给每个分片打质量分，低质量的分片少出题甚至不出题，避免从垃圾内容里造题。第二，生成后做二次校验，检查答案是否真的能在原文找到依据。第三，去重，包括语义重复。第四，剔除元问题，比如"文档提到了哪些内容"——这种题不需要理解就能答，会把分数虚高。
> 最终每条样本都带 `reference_context_ids`，标明标准答案来自哪个分片，这样检索指标才能算。

**C4 HitRate@K 和 MRR 的区别？**
> HitRate@K 只看"前 K 个里有没有"，是个 0/1 判断，衡量的是召回覆盖。MRR 看"第一个命中的排在第几位"，排名越靠前分越高，衡量的是排序质量。
> 举个例子：标准答案在第 3 位，K=5 时 HitRate 是 1，MRR 是 1/3。如果标准答案掉到第 10 位，K=5 时 HitRate 变 0，MRR 也变 0——这两个指标配合能区分"没召回到"和"召回到了但排得靠后"。

**C5 RAG 出问题怎么定位是检索还是生成？**
> 这正是我分两侧设计指标的原因。先看检索侧：HitRate@K 和 MRR 低，说明根本没找到正确证据，问题在检索；检索指标正常但 Faithfulness 低，说明找到了证据但模型胡说，问题在生成；Context Precision 低说明召回里噪声多。
> 报告会把这些指标并排展示，一眼就能看出是哪一环掉链子。

**C6 支持哪些文档格式？**
> txt、md、csv、json、docx、pdf 七类。扫描 PDF 走 OCR，其他走对应解析器。文档解析这块我没有追求覆盖所有格式，而是把主流格式做稳。

### D. Agent

**D1 ⭐ Tool Correctness 怎么算？**
> 工具名和参数都要完全匹配才算对。参数匹配支持嵌套结构，会比较 key 和 value，不是简单字符串比对。期望的工具调用序列从样本里的 tool_calls 字段读，实际序列从被测接口的响应里抽。

**D2 Argument Correctness 和 Tool Correctness 的区别？**
> Tool Correctness 更严格，工具名和参数都得对，是一个整体的对错判断。Argument Correctness 是"工具选对了，参数对到什么程度"，给出的是匹配度，能区分"用对了工具但参数差一点"和"完全跑偏"。
> 为什么要分开？因为这两种失败的修复方向不同：工具选错要改 Prompt 里的工具描述，参数错要改参数抽取逻辑。

**D3 Step Efficiency 怎么算？**
> 实际步数和期望步数做偏差惩罚。步数明显多于期望，说明绕路了；少于期望但任务没完成，说明跳步了。这个指标不需要 LLM，纯计算。

**D4 ⭐ 为什么强调"确定性指标"？**
> 因为可复现。LLM 评分有随机性，同样的输入可能给不同分，这种指标没法做回归——你改了一版 Prompt，分数涨了 0.02，你分不清是改得好还是模型今天心情好。确定性指标跑一百次结果一样，可以直接进 CI。
> 我的原则是：**有客观标准答案的，一律确定性计算；只有真正需要语义判断的，才交给 LLM。**

**D5 多轮对话怎么评？**
> 五个指标：Topic Adherence 看有没有跑题，Turn Relevancy 看每一轮是否回应了用户，Conversation Completeness 看信息是否给全，Knowledge Retention 看有没有记住前文，Role Adherence 看角色有没有崩。
> 多轮的关键是"跨轮"——很多问题单看某一轮没问题，连着看就发现自相矛盾或忘了前文。

**D6 Agent 评测的样本长什么样？**
> 统一的数据集模型，字段包括 user_input、contexts、tool_calls、reference、rubrics，还可以加业务自定义字段。tool_calls 里存期望的工具调用链，评测时和实际调用链比对。同一套模型能装 RAG、Agent、多轮三类样本。

### E. A/B 盲测

**E1 ⭐ 为什么用 MD5 哈希而不是 random？**
> 因为要可复现。用 random 的话，同一个样本第二天打开顺序可能变了，评审回看时对不上，投票就没法复核。MD5 是确定性的：同样的输入永远得到同样的顺序，但不同样本之间左右分布是均衡的，位置偏见照样能消掉。
> 一句话：**随机化是为了消偏见，确定性是为了能复核。**

**E2 三类对比分别适合什么场景？**
> LLM vs LLM 适合选模型；Endpoint vs Endpoint 适合选部署方案或检索配置；LLM vs Endpoint 适合"自建 vs 采购"的决策。

**E3 胜率怎么算？both_bad 和未答怎么处理？**
> 分别统计 model_a_wins、model_b_wins、ties、both_bad，未答单独计数。胜率只在有效对比里算，both_bad 和未答不混进胜率，否则会失真——两个都答得很差，不代表 A 输了。

**E4 盲测和自动评测冲突时信谁？**
> 看问题类型。事实性、检索准确性看自动指标，因为客观；表达偏好、有用性看盲测，因为主观。两者是互补证据，不是互相替代。如果冲突，说明指标设计可能没覆盖到用户真正在意的维度，这本身就是有价值的信号。

**E5 盲测样本量多少？**
> 取决于要区分的差异大小。如果要区分 5% 的胜率差异，样本量需求不小。目前这块是描述性统计，还没做显著性检验，这是明确要补的。

### F. RSI 自进化（重点，面试官最可能深挖）

**F1 ⭐⭐ 什么是 RSI？为什么要做这个？**
> RSI 是 Recursive Self-Improvement，递归自我改进。用大白话讲：**评测系统不只告诉你"哪里不好"，还能提出"怎么改"，并且自己验证改完是不是真的变好了。**
> 为什么要做？因为传统评测到报告就结束了，后面还是人看报告、人猜原因、人手动调。这个过程慢、不可追溯，而且改完到底有没有用，往往没有验证。RSI 把这四步串成闭环，并且强制每一步留痕。

**F2 ⭐⭐ 这和自动调参 / AutoML 有什么区别？**
> 有本质区别。自动调参是在一个固定的搜索空间里找最优参数，目标是分数最大化。RSI 优化的对象是**评测配置本身**——指标的判据、阈值、样本集，而且它要解决的核心问题是"这个改进是不是真的"，不是"分数是不是最高"。
> 更关键的是，自动调参通常没有治理层；RSI 我加了三道治理：留出集隔离、字段白名单、人工审批。因为改评测标准比调模型参数危险得多——标准一歪，后面所有结论都不可信。

**F3 ⭐⭐⭐ 怎么防止"自己证明自己"？这是这个模块最大的风险吧？**
> 对，这是我最重视的问题。四道隔离：
> 第一，**数据隔离**。用 MD5 稳定哈希把样本切成训练集和留出集，归因只能看训练集，验收只能看留出集。这样"从哪些样本总结问题"和"用哪些样本证明改进"永远不重叠。
> 第二，**标准冻结**。参考阈值在循环创建那一刻就从基线快照里冻结，后面不允许改。否则就会出现"边改及格线边验收"。
> 第三，**提案与验收分离**。提案生成和验收判定是两段逻辑，验收不关心提案说得多好听，只认留出集上的数字。
> 第四，**同模型风险上浮**。如果生成提案的模型和验收用的模型是同一个，风险等级自动升一级，逼着走人工审批。因为同一个模型容易偏爱自己风格的改动。

**F4 ⭐⭐ 为什么 holdout 要用哈希切分，不能随机切？**
> 因为要稳定。同一个循环会迭代多轮，如果每轮随机切，留出集一直在变，第 1 轮和第 3 轮的结论就不可比了——你甚至可能这轮在留出集上验证过、下轮它又跑回训练集去了，等于泄漏。
> 哈希切分保证：只要样本 ID 不变，切分结果永远一样。同时因为哈希本身是均匀的，整体分布仍然是随机的。

**F5 ⭐⭐ Patch 白名单具体限制了什么？为什么要这么严？**
> 只有 4 类配置对象、8 个字段允许改，比如 scenario_metric 的 prompt_override、pass_threshold，metric_definition 的 config 下的 prompt、definition、description、allowed_values。
> 限制有三层：值类型和范围，比如文本不超过 4000 字，阈值必须在 0 到 1 之间，单轮变化不超过 0.15；内容检测，出现 `sk-` 或 `Bearer` 这类凭据直接拒；模板字段检测，authorization、api_key、extra_headers 不许出现。
> 为什么这么严？因为 LLM 生成的提案本质是不可信输入。如果不设白名单，它可能改到数据库连接、endpoint 地址，甚至往里塞凭据。**白名单不是限制能力，是限制破坏面。**

**F6 ⭐ before_value 漂移校验是干什么的？**
> 提案生成时记录 before_value，写回时校验它是否还等于当前值。要同时对两个地方校验：冻结快照和实时实体。
> 解决的是并发修改问题：提案生成到你点采纳之间，可能有人手动改了配置。如果直接写，就会把别人的改动覆盖掉。校验不过就拒绝，让人重新生成提案。

**F7 ⭐ 版本表为什么 append-only？回滚怎么实现？**
> 审计要求。如果版本记录能被改，那"谁在什么时候改了什么"就不可信了。所以表只增不改，回滚也不是删记录，而是新增一条带 lineage 的回滚版本，同时给旧版本打标记。
> 这样任何时刻都能回答三个问题：当前是什么、历史上有哪些版本、每次变更的父子关系是什么。

**F8 ⭐ 为什么默认人工审批，不自动采纳？**
> 因为评测配置改错的代价很高——它会污染后续所有结论。自动采纳我只开放给低风险补丁，而且要求留出集至少 30 行，样本太少统计上不可信。
> 低风险指的是纯数值调整，比如阈值微调，且变化幅度受 0.15 限制。判据改写这种中风险改动，必须人看。

**F9 ⭐ 预算和收敛怎么控制的？跑飞了怎么办？**
> 五个硬上限：最多 3 轮迭代、每轮最多 50 行、总共最多 300 次 LLM 调用、最长 45 分钟、每轮最多 3 个提案。任意一个到顶就停，并且把停止原因落库。
> 收敛条件是连续 2 轮没有增益就停，不为了迭代而迭代。
> 进程重启的情况，启动时会把状态还是 running、但已经超过预算时长的循环回收成失败，保留已完成的结果。这是为了防止数据库里留一堆永远 running 的僵尸任务。

**F10 RSI 的测试怎么做的？**
> 6 个模块、42 个用例，按风险点分：
> - policy 测切分稳定性、阈值是否真的用冻结值、门禁的边界；
> - patch 测白名单、漂移、敏感信息、变化幅度、快照不被污染；
> - engine 测完整流程：等待审批、通过、拒绝、取消；
> - rollback 测版本只增不改、回滚精确恢复字段、lineage 正确；
> - diagnosis 测归因只统计训练集、LLM 聚类会过滤留出集证据；
> - api 测接口契约、409 冲突、403 开关、预览用候选快照。
> 全部用 mock 的 Judge，离线可跑，不花 API 费用。

**F11 ⭐⭐ 这个闭环在真实业务里真的有用吗？有数据吗？**
> （诚实版，推荐照这个说）
> 逻辑上是成立的，但我不会说它有大规模生产数据——目前是竞赛项目和个人项目阶段，验证的是机制正确性，不是业务收益。
> 我能拿出的证据是测试层面的：42 个用例证明了门禁、回滚、防漂移这些机制按预期工作；验收阈值 0.03 和 0.02 是行业里常用的最小可感知差异量级，不是我拍的。
> 如果上真实业务，我最想验证两件事：一是采纳的提案里有多少在两周后仍然有效，二是人工审批的通过率——如果通过率极低，说明提案质量不行；如果接近 100%，说明门禁太松或者人在走过场。

**F12 这个自进化会不会把指标改得越来越宽松，最后全是满分？**
> 这正是"受保护指标"和"增益门槛"要防的。第一，不是所有指标都能改，受保护指标不允许降；第二，阈值变化幅度单轮不超过 0.15，且必须在 0 到 1 之间，不能一路放到 0；第三，验收要求目标增益至少 0.03，光放宽标准不会带来真实增益，因为留出集的样本没变。
> 但说实话，如果只优化单一指标，长期确实有漂移风险。所以我留了扩展位：加对抗集和跨场景迁移校验，如果改进只在训练分布上有效、换一批样本就失效，就判定为过拟合，拒绝采纳。

### G. 工程与稳定性

**G1 ⭐ 长任务怎么不阻塞接口？**
> 用线程把任务从事件循环里摘出去，线程内部 `asyncio.run` 跑异步评测。接口层立即返回，前端轮询进度。逐行写入进度和日志，支持取消。

**G2 ⭐ 超时和僵尸任务怎么处理？**
> RAG 生成任务设 15 分钟超时。另外启动时做一次回收，把超时的 running 任务标记为失败，已完成的结果保留。这样不会出现"任务永远转圈"的状态。

**G3 并发怎么控的？**
> 盲测用信号量限制 3 路并发，避免把被测接口打挂、也避免触发上游限流。RSI 的候选评测是串行队列，因为 SQLite 单写锁，并发写会互相等，反而不如串行稳。

**G4 ⭐ 敏感信息怎么处理的？**
> 两层。一是响应脱敏，API Key 和 endpoint 的 Authorization 返回前打码；二是版本控制排除，`.env`、数据库文件、上传目录、构建产物都进 gitignore。
> 在 RSI 里还加了一层：patch 内容检测凭据特征，`sk-` 和 `Bearer` 直接拒绝。

**G5 测试覆盖到什么程度？**
> 原有 5 个模块的单元测试，加上 RSI 的 6 个模块 42 个用例。重点是关键路径和边界：状态冲突、漂移、权限开关、回滚、异常降级。没追求覆盖率数字，追求的是"改坏了能被测出来"。

**G6 如果线上出了 bug，你怎么定位？**
> 三层证据：任务级的 execution log、行级的 metric_scores 和 reason、接口级的 endpoint trace（状态码、延迟、原始响应）。基本能定位到具体哪一行、哪个指标、哪一步失败。

**G7 这个项目有什么技术债？**
> 四个明确的：没有登录认证和 RBAC；没有正式数据库迁移，靠 create_all 加运行时补列；A/B 盲测没做显著性检验；SQLite 不适合生产并发写。这四条我都知道该怎么补，只是当前阶段优先做了评测内核和 RSI。

**G8 如果让你重构，你会先改哪里？**
> 先加认证和权限，因为这是上线的前置条件。然后把数据库迁移换成 Alembic，再上 PG。技术架构上我会把任务执行抽成一个独立的 worker 层，现在是线程内跑，虽然够用，但不利于横向扩展。

### H. 竞赛与项目管理

**H1 比赛里你负责什么？**
> 独立完成全部技术实现：架构设计、评测内核、前后端开发、测试。另外负责方案设计和答辩材料。

**H2 评委最关心什么？**
> 一般是三点：解决的是不是真问题、技术方案有没有深度、有没有可验证的结果。所以我答辩时先讲痛点，再讲 RSI 的治理机制，最后给测试和数字。

**H3 这个项目和市面上的评测平台（LangSmith、Ragas 等）有什么区别？**
> 两类区别。第一，我把检索指标和生成指标放在同一套场景配置里，能直接定位是检索还是生成的问题，而不是分散在几个工具里。第二，RSI 这一层是大部分评测工具没有的——它们帮你评，但不帮你改，更不会验证改完有没有用。
> 另外我没有依赖第三方指标库，评判口径完全可控，这对需要业务定制的场景很重要。

**H4 为什么叫"中台"？**
> 因为它不是给某一个应用用的工具，而是给多个 AI 应用共用的一套评测能力：数据集、指标、Judge、报告、盲测都是共享资产，不同应用通过场景配置接入。

**H5 这个项目最大的创新点是什么？**
> RSI 的治理设计。自进化的概念不新，但"怎么让自进化不敢乱来"这一层是很多人忽略的。我把留出集隔离、阈值冻结、字段白名单、漂移校验、append-only 版本、人工审批串成了一条完整的防线。

**H6 如果给你更多时间，你会做什么？**
> 三件事：补认证和审计日志；给盲测加显著性检验；给 RSI 加对抗集和跨场景迁移校验，专门防过拟合。这三件都是"让结论更可信"的方向，而不是加功能。

### I. 压力题 / 不会的问题

**I1 ⭐ 你这个项目是不是玩具？有真实用户吗？**
> 我不会把它说成生产系统。它现在是一个完整的、有测试兜底的项目，验证的是机制正确性。真实业务验证还没做，这是事实。
> 但我觉得它解决的是真问题——我做的每一个设计决策，比如 error 和 0 分分开、场景快照冻结、盲测顺序可复现，都来自真实评测里会踩的坑，不是凭空想的。

**I2 ⭐ 你的数据量多大？**
> 目前是示例数据集规模，没有百万级样本。所以性能层面我更多是做了机制上的约束——分页、截断理由、限制每轮行数、预算上限——而不是做过大规模压测。这块如果上生产，需要重新做容量评估。

**I3 这个指标设计有理论依据吗？**
> 部分是有的，比如 Faithfulness、Context Recall 这些来自 RAG 评测的通用范式，HitRate 和 MRR 是检索领域的标准指标。但也有一部分是工程经验，比如 900 字分块、0.7 阈值。我不会说它们有严格的理论最优性，它们是经过实践检验的合理默认值，而且都做成了可配。

**I4 你说防止自证，但训练集和留出集都来自同一个数据集，分布一样，怎么能算独立？**
> 这是很好的质疑，确实同一个数据集切分只能防"样本级泄漏"，防不了"分布级同源"。所以我在文档里把对抗集和跨场景迁移校验列为下一步——用不同来源、不同分布的样本来验证改进是否真的泛化。目前能做到的是：至少不会用被改进影响过的样本来验收。

**I5 你刚才说的某个点我不太认同……**（被挑战时）
> 这个思路我理解，您说的角度是 XX 对吧？我当时的取舍是 XX，因为 XX。不过您提到的这点确实是我的盲区，如果按您的方案，可能会在 XX 上更好，但代价是 XX。您觉得这个权衡成立吗？
> **要点**：先复述对方观点确认理解，再说明自己的取舍理由，最后承认边界并反问。不要硬扛，也不要立刻投降。

> "这块我还没做到那么深，我当时的实现是 XX，如果按您说的方向，我会先去验证 XX，再决定要不要改。"
